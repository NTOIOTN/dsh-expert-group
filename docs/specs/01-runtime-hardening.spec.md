# DEG 运行时可靠性与容量收口规格书

> 状态：已通过 oracle 第 4 轮复审；已拆分为 `docs/tickets/` 的 30 张票据（票据经 oracle 第 3 轮审核通过，frontier 可用）；`ready-for-agent` 标签待 issue tracker 配置后发布
> 适用版本：dsh-expert-group 0.1.8+
> 依据：v0.1.7 代码评估（六路只读侦察 + oracle 评审）、ADR 0001/0002/0005、CONTEXT.md 领域词汇
> 范围：运行时正确性、恢复语义、容量生命周期、失败可见性、finalize 对账、发布门禁

## Problem Statement

DEG 在短时间、单会话的使用中表现稳定，但长时间运行、跨重启和容量逼近上限时，用户会依次遇到以下问题：

1. **并发配置不可信**：用户把「单个角色并发上限」从 10 改成 2 并保存，当前进程立即生效；重启 DSH 后设置页仍显示 2，但实际调度按快照里的旧值执行。用户无法解释为什么并发不符合配置，也没有任何界面提示配置来源已退化。
2. **容量只进不出**：父任务从不回收，64 个 fan-out 父任务全部结算后，第 65 次提交被永久拒绝。错误提示让用户「取消已结算的父任务」，但取消已结算任务是空操作，且没有任何删除/归档入口；该状态跨重启持续。
3. **持久化静默失败**：快照超过体积上限时，管理器直接跳过写盘、不写日志，只在内存保留最近一次违规记录；用户看到任务正常完成，重启后发现更新丢失。恢复失败（版本不匹配、结构非法、超预算）同样只写 warn，界面回到空树且没有错误态。
4. **等待与取消缺少兜底**：管理器内部已经支持分片超时计时与 `timed_out` 收敛，但公开工具与 Host 没有暴露该能力，也没有父级默认值；处于取消请求中的分片只等 child 回调，child 不回调就永久 running 且不能重试；续作 attempt 的归属无法证明时同样永久等待。root turn 等待也没有超时，卡住时只表现为「主代理一直 running」。
5. **恢复后能力投影不一致**：重启前已完成的任务在 Expert Group 侧栏可见，但查询、事件、重试都返回 404；能力字段仍投影为「可继续」，实际写操作被拒绝。用户被界面误导。
6. **恢复续跑越过 attempt 上限**：快照输入允许恰好 8 个 attempt，恢复时又会为中断分片追加一个新 attempt，结果变成 9 个，违反「每分片最多 8 次」的公开契约。
7. **finalize 制造可避免的拒绝**：插件已经能算出本批次应有的 admissionToken 集合，却仍要求模型原样枚举；模型漏记或多记一个 token 就得到 `incomplete-admission-token-set`，同一批次无法收口。错误码又不会显示在工具渲染文本里。
8. **配置字段名不副实**：`notificationHoldMs` 有 schema、有设置页、有提交校验、有 README 描述，但没有任何投递路径消费它。系统通知侧的 8 秒是终止 PowerShell 子进程的投递超时，不是横幅展示时长；两者不能混为一谈。该字段的去留与验收归《可观测性与体验规格书》。
9. **本地发布产物误伤门禁**：release gate 递归扫描仓库内所有 `.tgz`，只跳过依赖目录与 `.git`。用户本地执行一次 `npm pack` 后，门禁变红直到手动删除产物，即便该目录已被 gitignore。

这些问题的共同点是：**配置、容量、恢复、等待的语义没有形成闭环**，系统在「正常路径」之外没有可解释的行为。

## Solution

按四个交付面收敛：

**A. 配置一致性**：恢复后角色并发仍按当前 settings 解析；无法解析时回退到安全默认并在诊断中标注来源。所有公开设置字段必须真实生效，否则从 schema、UI、文档中移除。

**B. 容量生命周期**：一期只提供显式、root-only 的已结算父任务回收，自动回收范围冻结；容量判定不再永久堵死；重复 requestId 的幂等语义优先于容量拒绝；拒绝提示指向可执行动作。

**C. 失败可见性**：预算违规、持久化失败、恢复失败、等待降级进入结构化事件与运行时诊断；Expert Group 侧栏与设置页能展示必要的健康状态；提供基于权威证据的人工逃生入口。

**D. 语义一致性**：恢复后的任务在侧栏、查询、事件、动作之间保持同一套寻址与逐动作能力投影；恢复续跑遵守 attempt 上限；finalize 以「当前 root/run + epoch」定位整批、token 只作诊断；发布门禁只检查受版本控制的产物范围。

## User Stories

### 配置一致性
1. 作为 DSH 用户，我希望重启 DSH 后角色并发上限仍按最新保存值执行，这样设置页显示的配置与实际调度一致。
2. 作为 DSH 用户，我希望在诊断里看到并发上限的来源（当前设置 / 快照回退 / 非法值回退默认），以便解释任务为什么排队。
3. 作为 DSH 用户，我希望角色并发上限解析失败时界面有提示，而不是静默回退到 10。
4. 作为 DSH 用户，我希望任何在设置页出现、被 README 描述的配置项都真实生效；不再生效的字段从 schema、UI 与文档中删除。
5. 作为插件维护者，我希望快照不再把「构造期运行时默认值」当成恢复后的权威来源，以免新增配置项重复同类问题。

### 容量生命周期
6. 作为 DSH 用户，我希望可以显式回收自己已结算的父任务，以免 64 个历史任务后永久无法提交新任务。
7. 作为 DSH 用户，我希望容量拒绝提示给出可执行入口（回收任务、等待结算、调整上限），而不是「取消已结算任务」这种空操作。
8. 作为 DSH 用户，我希望重复提交同一 requestId 在容量边界仍返回原任务；若原任务已被回收，则按新任务处理，且这一语义在文档中明确。
9. 作为 DSH 用户，我希望回收动作有明确的归属校验，只能由当前 root 回收自己的任务。
10. 作为 DSH 用户，我希望回收后的任务不再出现在当前任务树中，也不会因重启而复活。
11. 作为 DSH 用户，我希望回收不会误删仍在运行、有未结算分片、仍被续作/重试引用或仍被等待账本引用的任务。
12. 作为 DSH 用户，我希望回收只有在持久化成功后才报告成功；落盘失败时状态保持不变并给出错误。
13. 作为 DSH 用户，我希望回收之后迟到的 child 回调或事件被忽略，不会复活任务或改写统计。

### 失败可见性
14. 作为 DSH 用户，我希望快照超限导致持久化跳过时能看到明确告警，而不是「任务完成、重启丢失」。
15. 作为 DSH 用户，我希望持久化写失败（瞬态重试耗尽、容量不足、代次失效）在侧栏或设置页有可读状态。
16. 作为 DSH 用户，我希望恢复失败时侧栏显示错误态与重试入口，而不是回到空树。
17. 作为 DSH 用户，我希望恢复过程中被拒绝的旧版本/超预算快照产生一次性通知与诊断记录，便于定位。
18. 作为插件维护者，我希望每次预算违规都产生结构化事件（资源名、上限、实际值、是否可恢复），而不是只有内存字段。
19. 作为插件维护者，我希望恢复事件失败不再被忽略返回值，而是进入诊断与告警。
20. 作为插件维护者，我希望事件历史裁剪后有 gap 标志或「最早可用序号」，客户端游标失效时能重新同步。

### 超时、取消与看门狗
21. 作为 DSH 用户，我希望把管理器已有的分片超时能力暴露到工具与 Host：任务级默认值、分片覆盖、明确计时起点与禁用值。
22. 作为 DSH 用户，我希望超时的分片收敛为 `timed_out`，保留 attempt 历史，并可以手工重试。
23. 作为 DSH 用户，我希望发出取消请求后，即使 child 不回调，分片也会在宽限期后收敛为终态，而不是永久 running。
24. 作为 DSH 用户，我希望归属无法证明的续作 attempt 在看门狗到期后转为「需要人工处理」的失败态，而不是永久等待。
25. 作为 DSH 用户，我希望超时与看门狗默认不开启自动重试，避免把失败放大成重试风暴。
26. 作为 DSH 用户，我希望超时配置只影响之后新建的分片尝试，不改变已经在运行的分片语义。
27. 作为插件维护者，我希望明确区分「管理器已终态」与「真实 child 已停止」：真实活动未排除前，不释放影响范围保护、不宣告全部工作完成。
28. 作为插件维护者，我希望看门狗收敛后，受影响路径的写冲突保护仍保持到独立证据证明 child 已停止（权威停止信号或可验证 fencing）；attempt generation 更新不算证据。
29. 作为插件维护者，我希望迟到回调按 attempt/generation 隔离，只进入诊断，不改变终态、不复活任务、不重复计数。

### 恢复与逐动作能力
30. 作为 DSH 用户，我希望重启后已结算任务在查询、事件、重试、取消、续作之间看到一个一致的动作集合：能做的显示为可做，不能做的给出原因。
31. 作为 DSH 用户，我希望冷恢复后的只读查询与只读事件可用，写操作被明确拒绝并说明需要当前 live root。
32. 作为 DSH 用户，我希望每个任务投影出逐动作能力（可读、可重试、可取消、可续作），而不是用一个「可继续」字段暗示全部权限。
33. 作为 DSH 用户，我希望恢复续跑时 attempt 数不超过每分片上限。
34. 作为 DSH 用户，我希望恢复时被中断的分片得到新的 attempt，而不是复活旧 child 或静默丢弃。
35. 作为插件维护者，我希望任务归属解析只有一个权威入口（活动绑定 + 已结算只读索引），避免侧栏与 RPC 各走一套。

### finalize 与等待
36. 作为主代理，我希望 finalize 只需要 admissionEpoch 定位当前 root/run 下的整批工作，不必原样枚举全部 token，以免漏记一个 token 就永久无法收口。
37. 作为主代理，我希望传入的 token 只用于诊断与回报，不影响收口集合；未知 token 被忽略并回报。
38. 作为主代理，我希望 finalize 仍然立即返回非终态 `waiting` 回执，真正的收口仍由同一 wait 账本承担，不能被改写成同步等待。
39. 作为主代理，我希望 finalize 拒绝时能看到稳定机器码与可执行提示。
40. 作为主代理，我希望等待账本的未结算工作数、等待开始时间、后代查询能力可以被诊断读取，以便判断「长任务」与「卡住」。
41. 作为 DSH 用户，我希望收口消息投递失败时收到一次性提示，而不是静默停滞。
42. 作为 DSH 用户，我希望有一个 root-only 的人工逃生动作，但只有在权威证据明确「没有活动后代」时才允许关闭等待批次；查询失败或状态未知时继续拒绝。
43. 作为插件维护者，我希望人工逃生与看门狗收敛都不会在真实 child 仍可能写入时释放写冲突保护或宣布任务完成。

### 发布门禁
44. 作为插件维护者，我希望 release gate 的 `.tgz` 检查只针对受版本控制的文件集合，未跟踪的本地构建/发布目录不会让门禁变红。
45. 作为插件维护者，我希望强制把 `.tgz` 加入版本控制时门禁仍然失败，避免检查被空泛化。
46. 作为插件维护者，我希望门禁失败信息说明「哪个扫描根、哪些目录被跳过、命中哪个文件」。

## Implementation Decisions

### 1. 并发上限来源模型

- 快照继续记录任务级显式 `concurrencyLimit`（它必须固化），但不再把「构造期默认值」当作恢复后的角色池权威来源。
- 恢复后的角色池解析优先级：当前 settings 解析值 > 快照中的显式角色级映射 > 安全默认值。
- 诊断对象新增 `source`（`live` / `snapshot` / `fallback`）与 `invalid` 原因；设置页与 meta 可读取。
- 解析函数抛错或返回非法值时保留现有回退值，但必须产生一次性诊断事件，而不是只在内存计数。
- 旧快照（缺少来源标记）按「尽量 live」处理；无法 live 时才冻结，并在诊断中标注。

### 2. 父任务回收（一期：显式、root-only）

- 一期只实现显式回收，**不做自动归档**；自动回收的触发条件、保留窗口与 TTL 明确留到后续规格。
- 回收前置条件（全部满足才允许）：
  - 父任务已结算（`completed` / `completed_with_errors` / `cancelled`）；
  - 没有 running / queued shard，没有未结算 attempt；
  - 没有被续作（continuation）或重试记录引用；
  - 没有被 turn wait 账本或 goal handoff 引用；
  - 调用方是当前 live root，且任务归属该 root。
- 与续作/重试互斥：回收与续作/重试在同一调度临界区串行；先到者生效，后到者得到「任务已回收」的结构化拒绝。
- requestId 语义：回收时清除该任务的去重索引；之后重复提交同一 requestId 视为新任务。文档与错误提示必须说明这一点，不保留墓碑（墓碑方案留给后续规格）。
- 持久化：回收先落盘，成功后才从内存与 UI 移除并返回成功；落盘失败返回错误且保持原状态。
- 重启与迟到事件：回收后的任务不再进入持久化投影；迟到的 child 回调、事件或续作请求按 generation/归属校验忽略，不复活任务。
- 容量拒绝结构包含：`resource`、`limit`、`current`、`reclaimable`、`hint`；hint 指向真实的回收入口。
- 幂等去重前置于容量判定：requestId 命中且任务未回收时直接返回原任务。

### 3. 持久化与恢复可见性

- 管理器维护最近一次持久化结果：`saved` / `skipped`（含原因：degraded、unmeasurable、oversize）/ `failed`（含分类）。
- 超限不再静默：产生结构化事件，并进入运行时诊断；事件不包含完整快照内容。
- 恢复结果（成功数、延迟数、拒绝原因）进入诊断。
- 恢复失败必须在 Expert Group 侧栏显示**错误态并提供重试入口**；通知只能作为补充，不得替代错误态与重试入口。
- 重试行为：重试重新读取当前持久化快照并重跑恢复流程；重试不修改持久化数据；失败时保持错误态与稳定原因码。
- 权限条件：只读查看与重试由当前会话用户触发；涉及写归属的动作仍按逐动作能力拒绝。
- 持久化状态：恢复失败不得清除、覆盖或重写磁盘上的快照；只有下一次成功恢复或显式回收才改变持久化内容。
- 恢复事件失败的返回值必须被消费；失败进入诊断，不得静默。
- 版本不匹配、结构非法、预算失败三种恢复拒绝原因拥有稳定错误码。
- 事件历史裁剪后维护 gap 标志或「最早可用序号」。

### 4. 超时、看门狗与「真实停止」边界

- 管理器已有 `timeoutMs` 输入、计时与 `timed_out` 收敛；本规格要求把它完整暴露：fan-out 分片可选 `timeoutMs`、父任务默认值、设置页可选的角色级默认值。
- 计时起点：attempt 进入 running 的时刻；取值 `0` 或 1000–86,400,000 毫秒（精度 1 秒），`0` 或未设置表示不启用；越界取值在工具与 Host 校验层被拒绝。超时只影响之后创建的 attempt。
- 取消请求记录请求时间；超过宽限期由运行时收敛为终态。收敛前先尽力调用 interrupt，但不依赖其回调。
- 归属无法证明的续作 attempt 记录 aging；超过阈值转为 `interrupted` 并带 `needs_attention` 标记；不自动重试。实现选择 `interrupted`（而不是 `failed`）是为了表达“逻辑轮次已终止但执行停止仍未确认”：影响范围继续保留，直到权威停止证据到达；`needs_attention` 让消费者无需把该场景误读成普通失败。
- **逻辑终态与真实停止分离**：管理器把 attempt 标记为 `timed_out` / `failed` / `cancelled` 只表示「不再等待该 attempt」，不表示真实 child 已停止。
- 影响范围保护（写冲突 scope）的释放条件只有一个：收到 child/session 结束的**权威停止信号**，或宿主提供可验证的写入 fencing 证据（能证明旧 child 的写入不再落地）。
- generation 替换只用于迟到事件隔离，**不作为 scope 释放条件**：generation 更新不证明旧 child 已停止写入。
- 状态转换：attempt 逻辑终态（timed_out / failed / cancelled）→ 迟到事件隔离生效 → 等待权威停止信号 → 释放 scope → 任务才可宣告完成。缺少任一步，任务保持「仍有活动」状态，不进入终态聚合、不发完成通知。
- 无法证明停止时的行为（fail-closed）：scope 保持，任务保持「仍有活动」状态，不进入终态聚合、不发完成通知；系统提供诊断与告警，但不提供「无证据即释放」的入口。
- 唯一另外的释放边界是进程重启：旧执行体随进程终止，恢复流程据此重建 scope 状态；重启前未释放的保护不跨越进程边界继续持有。
- 明确删除「root run 结束」与「人工释放动作」两条路径：两者都不能证明旧 child 已停止写入，因此不得作为 scope 释放条件。
- 迟到回调按 attempt + generation 隔离：只记录诊断事件，不改变终态、不复活任务、不重复计数。
- 人工逃生（root-only）：只有当权威查询明确「该 root 没有活动后代」时才允许关闭等待批次；查询失败、能力降级、状态未知一律拒绝，并返回原因码。
- root turn 等待本身仍不设自动超时释放。

### 5. 恢复寻址与逐动作能力

- 任务归属解析统一为一个权威入口：活动绑定 + 已结算只读索引。侧栏快照、查询、事件、动作全部复用。
- 任务能力投影为逐动作对象，例如「可读 / 可重试 / 可取消 / 可续作」；每个动作附拒绝原因码（无写归属、已终态、任务不存在（含已回收）、能力降级等）。回收不保留墓碑，因此回收后的查询与动作统一返回 `task_not_found`，这与票据 05 的去重语义一致。
- 冷恢复的已结算任务：查询与事件返回只读结果；重试/取消/续作分别按各自条件判定，拒绝时返回明确原因。
- 客户端严格按逐动作能力渲染按钮，不再用单一 `continuable` 推导所有动作。
- 恢复续跑复用 retry 的 attempt 预算判定；超限时中断分片保持 `interrupted` 并暴露原因，而不是追加第 9 次。

### 6. finalize 整批语义

- 批次定位键是「当前 root/run + admissionEpoch」；epoch 不脱离 root 解释为全局键。
- finalize 收口的是该 epoch 下的**完整有效 admission 集合**，由服务端枚举；调用方无需也无法通过 token 选择子集。
- `admissionTokens` 变为可选诊断参数：传入时用于核对与回报（未知/重复 token 被忽略并回报），不影响收口集合；未传时服务端直接枚举。
- 被 discard 的 ticket 继续排除在有效集合之外（保留现有语义）。
- 部分收口、按 token 子集处理不在本规格范围；若未来需要，必须另行定义未选 admission 的归属与生命周期。
- 不变量：finalize 校验通过后仍**立即返回非终态 `waiting` 回执**，登记到同一 wait 账本；真正收口由 turn-stopping 生命周期完成。实现不得把该工具改写成同步等待。
- 允许**逐 child 进度放行**：任一专家的精确关联 settlement 到达时，wait 账本可以只收口当前 turn-stopping 等待者（不结束 turn、不销毁记录、不关闭批次），让 root 在同一 turn 的下一个模型 step 消费该结算；最终结论仍只在整批静止后**一次性**投递，释放判据（精确完成通知或明确的「无 running 后代」）与「无超时」语义不变。
- 拒绝原因码保持稳定，并在工具渲染文本中附带 code 与可执行提示。
- 等待持续不产生用户可见提醒；后代查询降级与长等待只保留诊断（`capabilityLevel` / `reminderCount`），不再弹系统通知；收口投递失败仍产生一次性提示；等待本身仍无自动超时释放。

### 7. 发布门禁扫描范围

- 唯一策略：`.tgz` 检查只针对**受版本控制的文件集合**（由版本控制查询得出），未跟踪文件（包括本地 `.scratch`、`.market-submission` 目录）不参与检查。
- 不再使用「按 gitignore 排除」的第二条路线，因为现有 `*.tgz` 忽略规则会让该路线跳过全部目标文件。
- 门禁用例必须覆盖两侧：未跟踪目录中的 `.tgz` 通过；被强制加入版本控制的 `.tgz` 失败。
- 失败信息包含扫描根、跳过的非受控目录与命中文件。

## Testing Decisions

- **好测试的标准**：只断言外部可见行为——工具返回值、RPC 响应、诊断/meta 字段、持久化后重启行为、侧栏快照、逐动作能力。不断言内部私有函数、对象身份或字段顺序。
- **主接缝（Host 插件级）**：真实 `plugin.apply`，用可持久化 storage 替身承载快照；「重启」= 卸载后用同一 storage 重新 apply。通过公开工具面与 RPC 面观察行为。
- **辅助接缝（管理器/运行时级）**：仅当需要构造非法或越界输入（超预算快照、9 次 attempt、版本不匹配）时使用，属于现有先例的延续。
- **必测场景**，除正常路径外必须覆盖：
  - 并发：settings 改值 → 重启 → 派发；旧快照无来源标记的兼容路径。
  - 容量：显式回收；回收与续作/重试竞态（先到者生效）；回收后同 requestId 视为新任务；持久化失败时状态不变；回收后迟到事件不复活。
  - 持久化：快照超限 → 明确事件/诊断；持久化失败 → 重启后旧快照仍可读；恢复失败 → 错误态。
  - 超时/看门狗：超时收敛；取消后不回调 → 宽限期收敛；归属不明 → aging 后 `interrupted + needs_attention`；终态后迟到回调不改变状态、不释放 scope。
  - 真实停止：看门狗收敛后 scope 仍保护受影响路径，直到权威停止信号；旧 child 仍活动时新建 attempt 不得释放 scope；generation 更新不触发释放；缺少权威证据时 root 结束与人工动作都不得释放 scope，任务不得宣告完成，只有进程重启边界按恢复语义重建。
  - 恢复：同一任务的查询/事件/重试/取消/续作能力一致；attempt 上限；逐动作拒绝原因。
  - 跨 root 越权：非归属 root 的查询、回收、动作请求被拒绝。
  - finalize：只传 epoch、传多余 token、传重复 token、传旧 epoch、传错误 root，各自有明确结果；`waiting` 回执不变量。
  - 门禁：未跟踪 `.tgz` 通过；强制跟踪的 `.tgz` 失败。
- **边界用例不可删除**：64/65 任务容量边界必须保留一条真实边界用例（可在管理器级缩小 fixture，但不能只测缩小后的数字而失去边界意义）。
- **先例**：发布门禁的真实 apply 测试、fan-out runtime 的重启恢复测试、fan-out 续作的恢复拒绝测试、storage harness 的持久化失败测试。

## Out of Scope

- 自动回收、TTL、归档墓碑策略（后续规格）。
- finalize 的部分收口与按 token 子集处理。
- 模型 fallback、token/成本统计、provider 限流（见《模型路由与扩展能力规格书》）。
- 任务时间线渲染、轮询策略、bundle 压缩、a11y/i18n、通知字段去留（见《可观测性与体验规格书》）。
- 跨会话任务历史与全量索引。
- 自定义角色、手动派发、上下文继承。
- 自然语言自动拆分 fan-out。
- 给 root turn 等待增加自动超时释放。

## Further Notes

- 本规格与 ADR 0001（显式 fan-out、per-role 有界队列）一致；显式回收是该决策的补充，不改变「显式分片」的领域模型。
- 与《可观测性与体验规格书》的边界：`notificationHoldMs` 的去留、设置页展示、通知人工验收全部归体验规格；本规格只要求「公开字段必须真实生效或可移除」。
- 与《模型路由与扩展能力规格书》的边界：本规格不新增模型候选、限流或用量；只定义运行时状态机与能力投影。
- README 中「保存后才应用」「并发上限」「无超时」等描述需要随实现同步更新；旧规格书中的过时状态应标注为已被本文件取代。
- 实现顺序建议：并发来源 → 显式回收 → 持久化可见性 → 超时/看门狗（含真实停止边界）→ 恢复逐动作能力 → finalize 整批语义 → 门禁。前四项可独立交付，后三项依赖归属与等待账本的统一。
- 实施前验证（oracle 第 4 轮复审提出）：进程重启边界的正确性以「重启确实终止执行体所属进程」为前提；若存在能脱离该进程继续写入的 child 形态，恢复实现不得仅凭进程重启释放 scope。该前提应在对应实现票据中先行验证。
